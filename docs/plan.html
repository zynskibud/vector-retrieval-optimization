Vector Retrieval Optimization

Build the main vector indexes by hand in Python, Go, C++, and Rust, and check them against FAISS. Then run them in three self-hosted databases on 1.2 million Wikipedia vectors. Test filters, concurrency, updates and deletes, an embedding cache, and backup and restore. You write the code. Claude answers questions and reviews.

Rules

  • Each language folder has the same module names: flat, ivf, pq, ivf_pq, hnsw, diskann, plus shared npy, distance, and kmeans.
  • Each language has one bench program. It follows indexes/CONTRACT.md.
  • Only the tools computes recall, so all languages are measured the same way.
  • CLAUDE.md holds the fixed conventions for Claude and subagents.
0Setup and dataGet the vectors and the exact answers to measure against›

Learn first

  • Embedding: a vector that represents the meaning of a text.
  • Cosine similarity and dot product. Why they are equal for normalized vectors.
  • Ground truth: the exact top-k neighbors, found by brute force. It tests the index, not the embedding model.
  • Recall@k: the fraction of the true top-k that a search returns.

Build

  1. Set up a Python project with uv.
  2. Download 5 of the 145 files of maloyan/wikipedia-22-12-en-embeddings-all-MiniLM-L6-v2 from Hugging Face (about 2.9 GB).
  3. Normalize the vectors. Save them as a NumPy array, and save the metadata and text as Parquet.
  4. Remove 1,000 random vectors from the corpus. Use them as queries.
  5. Compute the exact top-100 neighbors of each query with NumPy, in chunks.

Done when

You have vectors.npy, queries.npy, metadata.parquet, and ground_truth.npy. You can explain recall@10 without notes.

1Indexes by hand, checked against FAISSWrite each index in Python, Go, C++, and Rust. Compare all four to FAISS.›

Learn first

  • Compiled and interpreted languages. Stack and heap memory.
  • Four memory models: Python (reference counting and garbage collector), Go (garbage collector), C++ (manual and RAII), Rust (ownership checked by the compiler).
  • Contiguous memory layout and SIMD for distance computations.
  • Threads in each language for parallel build and batch search: Python multiprocessing, Go goroutines, C++ std::thread or OpenMP, Rust rayon.
  • FAISS: a C++ library from Meta with a Python API. Each index class has the same methods: train, add, search.

Structure

  • 6 indexes × 4 languages = 24 implementations, plus FAISS as the reference.
  • Each language has one command-line benchmark program. It reads vectors.npy, queries.npy, and the settings, builds the index, runs the queries, and writes the result IDs, timings, and memory to a JSON file.
  • One Python script runs all programs, computes recall against the ground truth, and draws the plots. So all languages are measured the same way.
  • Pure Python loops are slow. If a Python build takes too long on 1.2M vectors, for example HNSW or DiskANN, run it on a 100k subset, and run the other languages on the same subset for that comparison.

Loop for each index

  1. Write the build and search in Python, Go, C++, and Rust, with the same algorithm and settings.
  2. Measure recall@10, latency p50 and p99, queries per second, build time, and peak memory.
  3. Run the same index in FAISS with the same settings on the same data. FAISS has no DiskANN, so compare DiskANN with Milvus in Phase 2.
  4. If recall differs between languages, one version has a bug: the algorithm is the same. If latency differs, find out why.

Done when

All four versions of each index are within a few points of recall of FAISS at the same settings. For each index, you have one recall-versus-latency plot with five curves: Python, Go, C++, Rust, and FAISS. You can explain every gap, for example garbage collector pauses in p99 latency.

3Metadata filteringVector search restricted to a subset of rows›

Learn first

  • Pre-filtering and post-filtering, and where each one fails.
  • Selectivity: the fraction of rows that pass a filter.
  • How each database combines a filter with its index.

Build

  1. Filters on views that keep 50%, 10%, 1%, and 0.1% of the rows.
  2. Exact ground truth for each filter, by brute force on the filtered rows.
  3. Filter support in your HNSW and IVF, in all four languages: skip nodes or list entries that fail the filter.
  4. The same filtered queries in each database.

Done when

You have a plot of recall and latency against selectivity for your indexes and each database. You can explain why very selective filters are hard for graph indexes.

4ConcurrencyMany clients at once: throughput and tail latency›

Learn first

  • Throughput (queries per second) and latency, and why p99 rises when load rises.
  • Threads, async I/O, and connection pools.
  • Locks and read-write locks. How a search can run while an insert changes the same graph.
  • Closed-loop load (fixed number of clients) and open-loop load (fixed arrival rate).

Build

  1. A load generator that runs 1, 2, 4, 8, 16, 32, and 64 concurrent clients.
  2. Make your HNSW safe for parallel searches, and for searches during inserts, in all four languages. Compare the locking tools of each language.
  3. Run the load against your index and each database. Record QPS, p50, p99, CPU, and errors.
  4. Repeat with a steady stream of inserts during the searches. Record the effect on search latency and recall.

Done when

You have a plot of QPS against p99 latency for each system as clients increase. You can name the point where each system saturates, and why.

5Updates and deletesChange the data after the index is built›

Learn first

  • Tombstones: mark a node as deleted without removing it from the graph.
  • Why a delete leaves the graph with fewer paths, and how recall can drop.
  • Graph repair, compaction, and rebuild. Postgres VACUUM and REINDEX.
  • Upsert: replace the vector of an existing ID.
  • IVF drift: clusters trained on old data fit new data less well.

Build

  1. Delete and update support in your HNSW and IVF, in all four languages.
  2. Delete 10%, 30%, and 50% of the vectors in each system. Recompute the ground truth on the remaining rows. Measure recall and latency.
  3. Update 10% of the vectors with new vectors. Check that searches return the new version only.
  4. Run compaction or rebuild. Measure recall, time, and disk use before and after.

Done when

You have a plot of recall against the fraction deleted for each system, before and after repair. No search returns a deleted or outdated vector.

6Embedding cacheSkip the embedding model for queries that were seen before›

Learn first

  • The query path: text → embedding model → vector → index search. Embedding is often the slowest step.
  • Cache key: a hash of the normalized text plus the model name and version.
  • Eviction policies (LRU, LFU) and TTL.
  • Hit rate, and why it depends on how often queries repeat.
  • Invalidation: a new model version must not use vectors from the old model.

Build

  1. Run all-MiniLM-L6-v2 locally, the same model that made the corpus vectors.
  2. A text query workload with repeats, for example a Zipf distribution over a pool of query texts from the Wikipedia titles.
  3. An in-process LRU cache first, then Redis as a shared cache for many clients.
  4. Measure hit rate, end-to-end latency with and without the cache, and memory for each cache size.

Done when

You have a plot of hit rate and p50 latency against cache size. A model version change makes the old entries miss.

Test procedure

  1. Run the 1,000 queries. Save the result IDs.
  2. Back up. Record the time and the file size.
  3. Delete the collection, table, or index.
  4. Restore. Record the time. Note whether the index must be rebuilt.
  5. Run the same queries. Compare the IDs and the row count.

Done when

Every query returns the same IDs after the restore, in each system. You have a table of backup time, size, and restore time.
